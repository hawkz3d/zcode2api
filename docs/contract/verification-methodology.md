# 验证方法论（captain 汇总）

> 本文记录本项目验证工作中**踩过的坑**与**确立的方法**。
> 触发：多处验证曾因方法不当而得出过弱或错误的结论。

---

## 一、DB「零污染」验证的正确方法

### 🔴 发现（Hilkiah，2026-10-15）

**老服务的 Python 进程并不长期持有 `accounts.db` 的 fd** ——
服务运行时有 15 个打开的 fd，其中**没有** `accounts.db`。
说明它是**按请求打开/关闭** DB，而非长连接。

**captain 复核**：确认。并发 30 个读请求期间，60 次 fd 采样**均未捕获到** `accounts.db` ——
打开窗口**极短**，无法用 fd 轮询可靠观测。

### 含义：几种验证方法的效力对比

| 方法 | 能发现什么 | 局限 |
|---|---|---|
| **`/proc/<pid>/fd` 轮询** | 长连接持有 | ❌ **本服务失效**（打开窗口极短，采样几乎抓不到） |
| **行数 / `integrity_check` 前后比对** | 结构性破坏、行增删 | ❌ **看不出瞬时写入**（改一个字段的一行，行数不变） |
| **DB 文件 mtime** | 任何写入（写入必更新 mtime） | ⚠️ 但**读请求也可能触发 checkpoint**，需配合日志判断 |
| **`PRAGMA data_version`** | 连接间可见的数据版本变化 | ✅ 较灵敏，需在两连接间比对 |
| **`total_changes` / `sqlite3` 审计** | 精确到语句 | 需进程内接入，外部不可用 |

### 推荐组合（captain 采纳）

```bash
# ① 前置：记录基线（mtime + 行数 + integrity + data_version）
DB=/…/data/accounts.db
BEFORE_MTIME=$(stat -c '%Y' "$DB")
BEFORE_ROWS=$(sqlite3 "file:$DB?mode=ro" 'select count(*) from accounts')
BEFORE_INT=$(sqlite3 "file:$DB?mode=ro" 'PRAGMA integrity_check')

# ② 执行被测操作

# ③ 后置：比对
AFTER_MTIME=$(stat -c '%Y' "$DB")
# 判据（分层）：
#   - 结构破坏 → integrity_check 变化  ← 最严重
#   - 行增删   → 行数变化
#   - 内容写入 → mtime 变化（含合法写入，需结合业务判断）
```

**读操作的判据**：**mtime 不应变化**。
（captain 实测：连发 10 次 `GET /admin/api/accounts`，mtime 未变 ✅ —— 证明读路径不写库。）

### ⚠️ 已知干扰源（会造成"看起来被写"）

| 干扰 | 说明 |
|---|---|
| **quota 定时刷新** | 服务周期任务会写库（captain 观察到 21:28 有一次写入） |
| **cron 巡逻** | `z2a_patrol.sh` 每 2 分钟一次，会调 admin API |
| **WAL checkpoint** | `journal_mode=wal` 下，checkpoint 会更新主文件 mtime，**即使无逻辑写入** |
| **假账号操作** | 测试若建/删账号，行数与 mtime 都会变（**属预期**，测后需清理） |

**结论**：判"零污染"时**必须排除上述干扰**，或**在无干扰窗口内**做前后比对。

## 二、WAL 模式的一个反直觉事实

**`journal_mode=wal` 但磁盘上无 `-wal` 文件** —— 这是**正常状态**：
无写入时 WAL 会被 checkpoint 并删除。**不要**据此判断"配置未生效"。

验证 WAL 是否生效应看 `PRAGMA journal_mode`，**不是**看有没有 `-wal` 文件。

## 三、快照复制的唯一正确方法

**禁止裸 `cp` 运行中的 WAL 库主文件**（会丢 WAL 中未 checkpoint 的数据，且可能损坏）。

正确方法：
```bash
sqlite3 "file:$DB?mode=ro" "VACUUM INTO '/tmp/snapshot.db'"
```
或 Python `sqlite3.Connection.backup()`。

本项目实现见 `internal/store` 的 `Snapshot()`（t3 交付，已验证）。

## 四、验证「实现是否做了 X」的三层判据

| 层 | 方法 | 强度 |
|---|---|---|
| **代码层** | 读源码确认逻辑存在 | 中（可能只在注释里声称） |
| **行为层** | 单测/手动触发，观察输出 | 强 |
| **契约层** | 对拍，与老服务逐字段比对 | 最强（但需对拍基线可信） |

**只做代码层 = 最弱**（"注释声称"与"真实实现"的差别）。
本项目要求：**至少行为层，关键断言要契约层**。

## 五、测试工具本身必须先自证（防假绿）

任何验证工具在用于判定前，必须证明：
1. **无假阳性**：同源比对应全绿（如 baseline vs baseline）
2. **无假阴性**：故意注入差异应被抓出
3. **退出码可用**：失败时非 0（供自动化门禁）

本项目对拍框架的自证记录：`docs/contract/review-evidence/captain-conformance-selftest.md`

## 七、「有证据外观 ≠ 有覆盖」（Hilkiah 发现，2026-10-15）

### 案例：`recent_results` 方向断言漏网

**事实**：契约（t1）写 `recent_results` 是「`[0]` 最新（前插）」，**实测恰好相反**
（6/6 账号 `at` 严格**升序**，`[0]` 最旧、`[-1]` 最新 → **后插**）。
captain 独立复核确认：**升序**。

**该错误逃过了三道关卡**：
1. t1 冻结（作者自己写错，且原判据把最旧值 `1791978426.71` 误读成最新）
2. **t8（Liche 43 项对抗核验，verdict=pass）**
3. t5 前审查

**漏网原因**：该断言有 `[黑盒] recent_results[-1]` 支撑 —— 但**只验了形状、没验方向**。
形成「**有证据外观、无方向覆盖**」的盲区。

**更严重的是对拍也看不见**：CR-16b 指出归一化把该字段整体 `replace_typed` 折叠 →
**前插/后插错误在对拍中完全不可见**，必须用**单侧断言**（不能只靠双服务对拍）。

### 方法论（captain 采纳并写入）

> **有引用 ≠ 有验证。有证据外观 ≠ 有覆盖。**
>
> 检查一条断言时，问三个问题：
> 1. **谁**验的？（作者自验 vs 独立验证）
> 2. 验了**什么维度**？（形状 / 方向 / 边界 / 顺序）
> 3. 该维度能否被**下游手段**（对拍/归一化）观察到？若不能 → **必须单侧断言**

**应用**：本项目所有"顺序/方向/递增递减"类断言，都必须有**显式的方向断言**，
不能只依赖"字段存在且形状正确"。

## 八、检测方法效力分级（captain 汇总）

Hilkiah 的 t5 审查给出了本项目**最强**的零污染检测法，值得记录：

| 方法 | 强度 | 说明 |
|---|---|---|
| **strace 写类 syscall 归因** | 🔴 **最强** | 全量测试 → trace 7835 行、写类调用 1417 条，**落在目标库的写/截断/删除/改名 = 0 条**；主库 open 模式为 `O_RDONLY` |
| `last_checked_at` 哨兵 | 🟠 强 | 比 mtime 更准：**quota 刷新会推进它，读不会** |
| mtime 前后比对 | 🟡 中 | 会被 WAL checkpoint 干扰 |
| 行数 / `integrity_check` | 🟡 中 | 看不出字段级瞬时写入 |
| `/proc/<pid>/fd` 轮询 | 🔴 **失效** | 服务按请求开库，40 秒 strace 显示**完全没 open 目标库** → 不仅"抓不到"，**根本推不出"没写过"** |

**补充事实**：`-shm` 文件 mtime 会推进，即使只读打开 —— 这是 **SQLite WAL 读模式机制必然**，
非实现缺陷。**不要**据此判断"有写入"。

## 九、SQLite URI 保留字陷阱（Hilkas 发现，captain 复核确认）

**问题**：`store.dsn()` 只转义 `%`，**未转义 SQLite URI 保留字 `?` / `#`**。

**captain 独立复核**（构造 `with?question.db`）：
```
Path() 返回: /tmp/…/with?question.db      ← 声称的路径
目录内实际文件: with / with-shm / with-wal  ← 真实落盘（`?` 被当查询串分隔符）
```
且 `Open` / `EnsureSchema` **全部返回成功、零报错** → **静默写错位置**。

**修复**（已验证有效）：`%` 之后追加 `%3F` / `%23`（**顺序不可反**，否则二次转义）。

**当前不触发**：生产 `.env` 是 `ZCODE_DATA_DIR=data`（相对路径、无特殊字符）。
但属"静默写错位置"，应修 + 补特殊字符路径单测。

**方法论**：凡是**字符串被嵌入另一套语法**（URI / SQL / shell / 正则）的地方，
都必须问「**目标语法的保留字有哪些？**」——只转义"看起来危险"的字符是不够的。

## 十、同一结论在不同语境下含义不同（Hilkiah 发现，captain 采纳）

### 案例：`ORDER:PASS` 在「引擎自测」与「真对拍」中含义不同

**事实**（captain 复核 `harness.py:1817`）：
```python
candidate = args.candidate or args.baseline
```
→ `--engine-selftest` 若未显式给 `--candidate`，则 **candidate = baseline**，
即**老服务自比老服务**。

**后果**：此时报告里的 `AD-accounts ORDER:PASS` 证明的是
**「引擎自身对同一服务是自洽的」**，**不是**「Go 实现顺序正确」。

**captain 曾把后者读成前者** —— 这是「证据外观 ≠ 覆盖」的又一实例：
**同一个字样，在两种语境下指的是两件不同的事。**

### 判据（captain 采纳）

> **报告必须显式区分语境。** 任何 `PASS` 字样都应能回答：
> **「这是在比谁和谁？」**
>
> - `baseline vs baseline` → 引擎自洽性
> - `baseline vs candidate`（不同服务）→ 跨服务契约等价
>
> 若报告无法一眼看出，**必须在报告头显式标注**。

### 附带：跨服务顺序验证的正确做法

Hilkiah 的做法可复用：
> Go 侧顺序正确性**另用自写探针直连生产库快照验证**（6-id 序列与老服务 API 实测逐项一致），
> **不依赖** `--engine-selftest` 的 ORDER 行。

## 十一、「三问判据」：折叠容器时必答（Hilkiah，2026-10-15）

针对**归一化折叠**（`replace_typed`）这类规则：

> ① 折叠的是**容器还是标量**？
> ② 折叠后**哪些维度仍可辨**？（逐维度构造对照**实测**，不是读代码推断）
> ③ 被折叠的维度里，**有没有「持久契约」混在「进程态」里被一并扔掉**？

**本项目三次同型漏网都栽在第③问**：

| 编号 | 被折叠的容器 | 被扔掉的持久维度 |
|---|---|---|
| CR-16b | `$.accounts[*].recent_results` | **顺序方向**（前插/后插） |
| CR-35 | `$.accounts` | **顺序**（provider 组序 × created_at） |
| CR-37 | `$.entries` | **顺序方向**（ts 严格递减） |

**完备性结论**（Hilkiah 穷举）：`normalize.rules.json` 共 **22 条**，
其中**容器级恰好 3 条**（`$.accounts` / `$.accounts[*].recent_results` / `$.entries`），
**逐条对应已定罪的 CR-35 / CR-16b / CR-37** → **无第四处漏网**。

**这条完备性论证的价值**：它把「还有没有第四处」从**猜想**变成**可复核的穷举**
（`len(rules)==22`，分类可复跑）。

## 十二、「一致地错」——对拍类验证的根基性假绿（Liche 发现，2026-10-15）

### 事故形态

**Liche 开发对拍器时真实踩中**：
他的 worktree 环境里 `${ZCODE_ADMIN_KEY}` 变量解析失败 → 被 shell expand 吞成**空串**
→ **两侧（baseline 与 candidate）都带着空 key 发请求** → **两侧一致返回 401**
→ **旧引擎 L1/L2/L3 全绿**（因为 L1 只比「两侧是否相等」）
→ **只有 ORDER 层报红**（它断言的是绝对方向）

### 结论：**L1「两侧相等」不是正确性判据**

> **对拍的本质是比较两个对象。若两者「一致地错」，对拍会判通过。**
>
> 假绿条件：**被测双方共享同一个错误来源**（同一个错误的配置、同一个被吞掉的变量、
> 同一个错的前提），此时**相对比较无法发现绝对错误**。

### 治本三件（Liche 已落地，captain 复核）

| # | 措施 | 说明 |
|---|---|---|
| ① | **占位符保留 + 发送前守卫** | env 缺键时**保留 `${VAR}` 占位符**而非吞成空串；发送前硬 FAIL（哨兵 `missing-env-placeholder-hard-fails-before-send`） |
| ② | **status 绝对锚** | case/步级 pin **契约实测码**（41/47 case 已 pin）；两侧**各自等于 pin** 才绿，而非仅"两侧相等" |
| ③ | env 向上搜索 | 适配 worktree 工作目录 |

**②的意义**：它把 L1 从「相对比较」升级为「**绝对断言**」——
即使两侧一致地错，只要不等于契约实测码，仍会红。

### 判据（captain 采纳为通用原则）

> **任何「对比型」验证，都必须至少有一条「绝对锚」。**
>
> - 对拍（baseline vs candidate）→ 要有 status pin / 契约实测值锚
> - 回归测试（before vs after）→ 要有独立的期望值（而非只比"没变"）
> - 差分测试（A vs B）→ 要有至少一侧的绝对判据
>
> **纯相对的验证 = 只能发现"变化"，不能发现"错"。**

### 附带趣闻（证明了 CR-36 判据有效）

Liche 给 `GW-models` pin 时**凭印象写了 401**，被 L1 的 detail 输出当场纠正为 **200** ——
因为生产未配 gateway key 时放行（契约实测语义）。
**「[实测] 必须答得出对应命令」这条判据，在他自己的新代码上再次奏效。**

## 十三、绝对锚本身也有缝（Liche 自查，2026-10-15）

§十二 说「要有绝对锚」。但 Liche 用同一把刀审自己刚写的 ASSERT 层，
发现**锚本身有两处缝** —— 这条补充让 §十二 更完整。

### 缝①：类型缝 —— `True == 1` 在 Python 里为真

**形态**：断言谓词用泛 `eq`（Python `==`）时，
`{"count": true}` 与 `{"count": 1}` **互判为真**。

**后果**：若 candidate 把契约的 `count:1` 实现成 `count:true`（**正是 ADR-002 型漂移**），
`eq:1` 两侧同绿 → **断言从「绝对锚」退化成「类型盲」**。

**治**：`eq_strict` —— **bool 与数字永不互判**（int/float 同值仍互判，因 JSON 里 1/1.0 同数非契约面）。
`in` 谓词同修。

**哨兵**：`assert-eq-strict-bool-vs-int` 三态实测（`{count:true} vs eq:1 → 红`、`{count:1} → 绿`、`{count:true} vs eq:true → 绿`）。

**判据**：**写断言时，类型是契约面的一部分。**
`eq` 的语义应当是「值与类型都相等」，不是「Python 认为相等」。

### 缝②：共享源盲区 —— 两侧误连同一个库

**形态**：若 Go candidate **误连生产库**（`.env` 的 DATA 路径指同一文件 —— **集成期完全可能**），
则 lifecycle 序列中**两侧在同一库里各建各删假账号**：
- 各找各的 id → 都在
- 所有跨侧对比与单侧断言 → **全绿**

**治**：新谓词 `find_by_prefix_missing:"liche-lc-dummy-{{OTHER}}"` ——
**本侧列表出现「对侧」假号前缀即红**。配套自动变量 `{{OTHER}}` / `{{SAME_SOURCE}}`。

**诚实边界**（重要）：同源自比时两侧必同库互见 → `unless_shared_source` **如实 skip**。
> 这承认了「无证据」，但**不伪造红、更不伪造绿** —— 是 §「skip ≠ 绿」的机制化。

跨服务正式对拍时**强制生效**。

### 五层判据至此全部经受过同一把刀

`status-pin` / `ORDER` / `ASSERT` / `ST-DOM` / `sentinel` —— **每一层都被问过「两侧各以什么错法能同过这条」**。

**这条自审方法可复用**：
> 写任何断言/验证后，问：**「什么样的错误能让这条断言仍然通过？」**
> 若答案非空，那条断言就还不是绝对锚。
